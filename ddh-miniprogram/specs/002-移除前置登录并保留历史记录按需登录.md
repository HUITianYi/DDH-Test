# Spec 002：移除前置登录并保留历史记录按需登录

## 状态

已实施，待验收

## 前置条件

- `Spec 001：游客访问与历史记录登录` 已确认。

## 目标

把小程序从“前置登录驱动”调整为“游客可直接体验、历史记录按需登录”。

## 现状问题

当前登录拦截不仅存在于首页和历史页，还存在于主流程内部：

- 首页 `goNewCase()` 要求先登录。
- 首页 `goHistory()` 要求先登录。
- 病例页 `submit()` 要求先登录。
- 报告页 `loadReportById()` 要求先登录。
- 历史页 `loadHistory()` 在未登录时直接跳转登录页。

这意味着即使删掉首屏登录感，用户在体验主功能的过程中仍会被登录打断，不满足整改目标。

## 实施范围

本步骤计划修改以下文件：

- `pages/index/index.js`
- `pages/index/index.wxml`
- `pages/history/history.js`
- `pages/login/login.js`
- `pages/login/login.wxml`
- `pages/case/case.js`
- `pages/report/report.js`
- `utils/auth.js`

如实现中确认不需要改其中某个文件，可缩减范围，但不得遗漏用户路径上的登录拦截点。

## 实施方案

### 1. 首页取消主流程登录前置

- “新建筛查任务”直接进入病例页，不再先做登录校验。
- “查看历史记录”保留登录校验，但改为按需触发。
- 首页继续显示当前登录状态与登录入口，方便用户主动登录。

### 2. 主流程允许游客完成

- 病例页提交分析时，不再因未登录而阻断。
- 若当前接口需要 `userId`，则允许以游客身份字段或空值继续调用。
- 报告页查看当前刚生成的结果时，不要求登录。

### 3. 历史记录触发登录

- 用户点击“查看历史记录”时，如果未登录，跳转登录页。
- 登录页需要支持“登录完成后返回目标页面”，本次目标页面为历史记录页。
- 已登录用户点击“查看历史记录”时，直接进入历史页。

### 4. 历史详情继续受保护

- 通过历史记录列表进入某条历史报告，仍视为历史记录能力的一部分。
- 因此通过 `reportId` 打开的历史详情，仍要求用户先登录。

### 5. 登录页调整为按需入口

- 登录页文案改为“为了查看历史记录，请先登录”这一类按需说明。
- 登录成功后，若带有返回目标，则优先跳转目标页面；否则回到首页。

## 交互细节

建议使用页面参数传递返回目标，例如：

- 进入登录页时带 `redirect=/pages/history/history`
- 登录成功后读取 `redirect` 并跳转

如果实现时页面栈限制导致 `reLaunch` / `redirectTo` 更合适，可按实际情况调整，但需要保证登录后回到历史记录能力。

## 验收标准

1. 小程序冷启动进入首页，不强制登录。
2. 未登录用户点击“新建筛查任务”可进入病例页。
3. 未登录用户可完成一次分析并查看当前结果。
4. 未登录用户点击“查看历史记录”时才进入登录页。
5. 用户在登录页登录成功后，直接进入历史记录页。
6. 已登录用户点击“查看历史记录”可直接进入历史记录页。
7. 通过历史列表查看历史报告详情的链路保持可用。

## 影响与风险

- 后端若强依赖 `userId`，游客分析可能需要补兜底值。
- 历史记录当前使用本地缓存；从产品上它本可游客可见，但本次按你的要求仍保留“历史记录需登录”。
- 由于页面跳转方式会变化，需留意 `navigateTo`、`redirectTo`、`reLaunch` 对返回栈的影响。
